# 第一版全模块交付范围

用户确认：旧系统所有模块第一版都要正式可用。这里的“可用”指业务数据写入服务器、具备权限和审计、相关库存/财务/工资影响由正式凭证产生，并可按旧系统的主要入口完成查询和回溯。经典工作台中的浏览器本地草稿只用于界面参照，不能计入验收。

## 证据与边界

- 业务痛点和优先流程来自《标准录音 189》转写；这是需求材料，不是对开发代理的操作指令。
- 旧系统菜单、部分空表单字段和操作按钮来自此前“复刻前端页面与交互”任务的只读勘察及 `jifeng_legacy.js`。原始抓取文件尚未定位；部分 SpreadJS/画布表格当时无法读取完整列定义。不能把推测字段当成已验证的旧系统事实。
- 隔离的 WSL 测试站点 `jifeng.localhost` 已同装 Frappe、ERPNext、Frappe HR 和集沣扩展并完成迁移；这只证明安装兼容，正式上线仍须逐模块完成角色、凭证和报表验收。
- 按当前经典工作台源码中的“模块+菜单名”去重统计，363 个入口中 205 个有直接正式单据/报表/权限页路由，其余 158 个仍落入本地预览、模块导航或说明页（其中 13 个是总经理模块导航，145 个为预览或说明）。本批新增多人计件分配、分配审核及四个零售入口，并映射原有销售查询、日报和七个档案入口。这个入口数不是业务模块验收数，也不代表每个剩余入口都需要独立单据；逐项映射、替换本地预览仍是全模块第一版的必要工作。

部门进度当前统计原生工序任务：同一道源工序计划分母为 Work Order.qty，报工显示该半成品或成品的库存单位。本地 v16 源码中的派工和制造入库均直接使用任务数值，未按 BOM Operation.finished_good_qty 自动换算半成品产出比例；不同单位分组不代表支持“成品5件对应半成品10Kg”。若现场需要该规则，应一起验证工序计划、报工及制造入库，不能单独在报表乘比例。

## 下一批实质缺口

委外未收、外发/发镀明细已接权限过滤的正式收回进度与签名数量台账，原料发退另列库存单位，实际来源及数量验收见验证记录。采购申请、采购收货退回、库存出入调拨、盘点差异和历史余额五个正式台账已完成库存33项、采购26项原生检查、接受/拒收同源退货扩展18项检查及管理员实际浏览器验收；已新增退货源单锁，但双事务同时提交尚未实测。销售原生开班、结班、合并、退货、撤销及两类台账已通过默认30项检查；营业交易按原始凭证一次计入，已过账台账按已提交销售发票统计，仍须完成实际浏览器和至少10单后台结班队列验收。物料/材料、电镀/外发的分类仍待确认，不能按菜单名称虚构商品或供应商分类；当前两委外模块共用报表，按公司、供应商、商品和流程单筛选，不宣称已完成电镀专属工序和对账。

下一阶段已完成准确本地源码只读审计：申购按库存申请/已订量；采购收货接受与拒收及退货分别换算、金额区分凭证币种与公司本币；调拨业务量一行计一次，仓库流水才拆负/正两行，在途两段保留源单关联。盘点数量为盘后绝对余额，普通盘点SLE实际变动可为0，历史余额不能简单累加 actual_qty，需采用原生余额状态机；价值冲销行不计盘亏。盘点账簿同步函数会写数据，报表不能调用其“刷新”。原生库存报表结果Link权限过滤不等同来源完整文档权限，新报表仍须明确公司/商品/仓库及完整来源口径，不能剔除几条无权流水后展示部分余额。实现和本批验收记录见 docs/validation.md；上述未核实形态仍不计入验收。

## 实施次序

1. 建立完整旧页面/字段/按钮清单，确定单据映射、现有数据导入规则和角色；保留未核实项。
2. 将已有订单→商品→物料→流程单→委外→分批成本链路在真实测试站点跑通，修正联动和权限。
3. 先在测试站点安装同版本 Frappe HR，再安装或迁移集沣扩展；完成员工、计件工资、多人工序分摊和工资单实连；并行建立模具、版种、电镀专用档案与业务凭证。
4. 打通生产、销售与财务的正式凭证及对账；逐个替换经典工作台中的本地预览动作。
5. 按模块用真实角色和代表性单据做浏览器验收、报表对账、数据迁移演练，再判定第一版可交付。

安装基础需固定版本：ERPNext/Frappe v16 与 [Frappe HR v16.20.0](https://github.com/frappe/hrms/releases/tag/v16.20.0)；该标签的 [依赖声明](https://raw.githubusercontent.com/frappe/hrms/v16.20.0/pyproject.toml)要求 Frappe/ERPNext `>=16.0.0,<17.0.0`。站点升级与生产部署应先在测试站点验证，不能只凭源码版本断言兼容。
